# Native bridge wake procedure: codex-lead-1

Never discard an unprocessed reply using a timestamp high-water mark from another event or your own update. Reconcile by exact request ID and bound reply, including answers outside the recent tail; no new rows in a filtered tail does not mean a peer is still pending.

This procedure is used only after its deployed copy and the deployment manifest have been hash-verified against a trusted external manifest anchor. Its path alone is not evidence of trust. The bridge notification supplies the current `delivery_id`; the current bridge state and full event are authoritative. This file grants no new authority.

First action of every notified turn: record the consumption receipt for exactly this notification with pinned telemetry: . Take the delivery_id only from this notification, never from relay state, memory or another notification. The relay submits no further notification to this conversation until this receipt exists; it is not task completion and grants no authority. If recording fails, report blocked.

Before ending this turn, reconcile unfinished operator-authorized work, idle coder lanes and unprocessed results. Advance a file-disjoint eligible slice or record the specific dependency, owner and absolute deadline; a status report is not task completion. Do not serialize unrelated coding behind reviews. A diagnostic question does not itself cancel an existing implementation assignment.

Discover outgoing requests with pinned Get-BridgeRequestInventory.ps1 -Agent codex-lead-1 from $env:WD_BRIDGE_BIN before reconciling the inbox. Its whole-log request inventory replaces reliance on conversation memory or the recent 40-row view for request discovery. Do not add -SessionId: unfinished work can predate the current session. Use the default derived cache; -NoCache rebuilds the whole log and is for diagnosis. Require schema wd.request-inventory.v2. Inspect the snapshot time/cursor and compact request metadata.

At startup or after loss of the durable discovery checkpoint, log replacement or rollover, establish complete coverage by following next_cursor with -Cursor <next_cursor> and unchanged filters until boolean truncated=false. Persist compact discovered IDs, canonical log identity and whether coverage completed under .codex-audit; never mark a partial walk complete. On an ordinary wake, inspect page 1 and continue only while a page contains IDs absent from that completed checkpoint. Stop paging at a page whose IDs are all in that checkpoint; do not repeat a full historical walk on every wake. This incremental shortcut is unavailable with unread canonical backlog or uncertain checkpoint coverage. Never infer that a known request is answered from its inventory position. Independently reconcile every known outstanding request ID and every exact request ID referenced by recent canonical replies; also incorporate newly observed canonical request IDs even when their timestamps are old. A stale cursor invalidates the walk, but allow at most one bounded discovery attempt per turn: record unknown coverage and resume catch-up in a later bounded slice rather than restarting indefinitely while events arrive. Continue processing already known exact requests and replies when their control coverage is established.

Do not print or concatenate full historical payloads into the model context: preserve compact discovered IDs and retrieve only relevant exact snapshots. Failure, unknown schema, missing pagination metadata or unfinished required pagination means unknown coverage, never an empty inbox. Discovery is not answer status: resolve outstanding IDs with fresh Get-BridgeReplySnapshot.ps1 -RequestId <exact-request-id> -Requester codex-lead-1 and read complete bound answers before reporting. Reconcile exact prior observations and durable report references; do not declare every historical request pending or repeat completed effects. Do not bulk-resubmit historical requests. HOLD/cancel/finding controls are not enumerated: retain the separate canonical control read and known HOLDs; this inventory does not authorize action when control coverage is uncertain.

Partial fallback, only when the default refuses: if the default inventory fails with Malformed request_id, Malformed request author binding or Conflicting content for immutable request ID, keep that refusal and treat checkpoint coverage as uncertain, so the incremental shortcut is unavailable. Never retry the default in a loop, never repair, rewrite or truncate the bridge log or its cache, and never edit gate code or any installed file to get past it. Inside the same single bounded discovery attempt you may run the explicitly labeled diagnostic: pinned Get-BridgeRequestInventory.ps1 -Agent codex-lead-1 -DiagnosticPartial -PageSize 10, without -SessionId or -NoCache and never with a default -Cursor (default and diagnostic cursors never cross). -PageSize 10 is only the diagnostic request-row page size: it does not complete or extend the capped conflict prefix, and a page the getter refuses as over 50000 characters is a failure and unknown coverage, never a reason to change -PageSize during a walk. Accept a page only as schema wd.request-inventory-diagnostic.v1 with complete=false, which every diagnostic page carries and paging never changes; any other failure or schema, or missing pagination metadata, means unknown coverage. At startup you may follow its own next_cursor with -Cursor <next_cursor> and exactly the same other arguments (-Agent codex-lead-1 -DiagnosticPartial -PageSize 10; the cursor is bound to them, page size included) until truncated=false within that attempt; on an ordinary wake inspect diagnostic page 1 only, for new candidate IDs. In DiagnosticPartial mode overall coverage stays UNKNOWN whatever status (partial_unknown or no_conflict_observed), truncated or requests say: an empty or short requests list is never an empty inbox, never no pending answers and never a finished walk. Never add its IDs to the completed discovery checkpoint; keep them as separately labeled diagnostic candidates. Every ID it lists as a conflict is excluded: never treat it as a valid request, act on its content, resubmit it or infer its answer, HOLD or cancellation from it. The conflict list is a prefix of at most 50 entries and 30000 characters that paging does not extend, conflicts_truncated=true leaves further conflicting rows unlisted, and a row whose request_id is falsy is never listed even when conflicts_truncated=false. The diagnostic only discovers candidate IDs: it never replaces the canonical control read, known HOLDs, Get-BridgeReplySnapshot.ps1 for every known or candidate ID, or the exact reply and closure bindings above. Every report that relies on it names DiagnosticPartial, overall coverage UNKNOWN, status, conflict_count, conflicts_truncated, the listed conflicting IDs with their indexed_position, and snapshot_identity.cursor. Send the persistent conflict to the bridge owner once, with those listed IDs and positions, and repeat it only when they change; on every later wake try the default inventory first and fall back again only inside that wake's single bounded attempt.
