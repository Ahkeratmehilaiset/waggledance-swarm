## What was tried

`waggledance/core/hex_topology/ring_messaging.py::deliver_batch` — precomputed
per-cell relation sets (`neighbor_sets`, `parent_by_cell`, `child_sets`) once
per batch, replaced `neighbors_of()` + topology dict navigation with O(1)
frozenset membership checks. Implementation was inlined into `deliver_batch`
to avoid extra Python function-call overhead per message; `deliver_one`
preserved unchanged as the public single-message API.

Behavior was verified: `test_deliver_batch_parity_with_deliver_one_for_mixed_kinds`
exercised every kind + blocked_reason path and confirmed batched output is
field-identical to per-message `deliver_one`. Empty-batch + once-per-batch
index build also pinned. 111/111 hex tests passed.

## Why abandoned

Microbench against snapshot `72d580beb304` (5 BEFORE + 5 AFTER alternating
runs on the same machine):

| Operation | Count | BEFORE median | AFTER median |
|---|---:|---:|---:|
| `deliver_batch ring_request` | 20000 | 44.46 ms | 52.65 ms (~18% **slower**) |
| `deliver_batch child_to_parent` | 20000 | 37.41 ms | 50.20 ms (~34% **slower**) |

Root cause: at the bench workload (single large 20k-message batch), the
constant cost of building the relation index for the synthetic 1000-cell
topology (1000 × 3 frozenset constructions) is paid once and amortizes well,
but the per-message savings are smaller than the original cost of `sorted()`
on a 6-element list (Python's sorted-on-tiny-list is ~1 µs and CPython
optimizes that path heavily). The dominant per-message cost is `validate()`
and `RingDelivery` frozen-dataclass instantiation, neither of which the
relation index touches. The architectural shape is correct (O(1) set
membership > O(N) sort+list-in), but the specific Python code path doesn't
benefit at this scale and topology size.

## What this means

The architectural pattern Codex's R18 scout report described **is correct**.
But for the current product (no production callers of `deliver_batch` —
verified via repo grep, only the microbench and test suite use it), the
relative ordering of costs means the ~5 ms saved on relation lookups is
swallowed by the ~5 ms spent building the index, leaving zero or negative
net win at 20k batch.

The fix would pay off if:
- batches were SMALLER (so per-message savings compound across many
  index-build calls — but that's an even worse case for amortization, so
  no, this would not help either),
- batch sizes scaled to MILLIONS (where the constant index-build truly
  becomes negligible),
- the topology had MUCH HIGHER neighbor degree (so `sorted()` on neighbors
  became expensive — typical hex degree is 6, capped),
- OR a follow-up moved `validate()` and `RingDelivery` construction onto
  faster paths (slots dataclass without frozen, batched validation pre-pass).

Of these, only the last is independently valuable, and it belongs to a
different scout candidate.
