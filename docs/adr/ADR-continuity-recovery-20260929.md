# ADR: durable bridge continuity after a lane stops

Status: proposed, 2026-09-29. This document grants no deployment, merge, release, runtime, or HOLD-override authority.

## Observed failure and immediate slice

An expired claim can be archived while its `release/stale_lease` event has no `to` recipient. `Watch-Bridge.ps1` wakes addressed lanes; a release addressed to nobody cannot wake the former owner or its dispatcher. `Get-BridgeNextAction.ps1` can also prefer an active own claim over an older open request, so a pending request can remain unseen until the claim is released and the lane is woken again. A queue acceptance is not a completed turn or a completed task.

This slice changes only `Invoke-StaleClaimSweep.ps1`: after archive, the release is addressed to the claim's syntactically valid owner. It also addresses the original dispatcher only if a bounded, stable event-tail read finds a unique `wake_request/assigned` for the exact task and owner, whose `expected_responders` UUID and session match the archived claim. The dispatcher envelope must also contain a valid request ID, agent UUID and session ID *before* it is returned: otherwise a StrictMode payload dereference after archive can suppress even the owner's release event. Two distinct request IDs are ambiguous even when their sender is the same; exact duplicate copies of one request may be deduplicated. A task-id prefix is not dispatcher evidence. If the event is missing, too old for the tail, ambiguous, malformed, or the snapshot is unavailable, only the owner is addressed. The release remains a `system` event, and the payload carries the archived claim identity plus any observed dispatcher request identity; it does not impersonate either agent. Event emission remains best-effort after archive. A release is a signal to re-evaluate the queue, not permission to resume a HOLD, cancel a cancellation, reclaim a scope, or declare completion.

## Permanent correction

The immediate continuity guard targets the native Lead and Tools lanes only. Claude Monitor remains unchanged. This ADR is not an implementation or approval of the whole Bridge V2 plan.

1. Classify each committed bridge event before waking. Use a closed allowlist for *demonstrably benign* informational notices. A bound reply, correction, veto, HOLD, cancellation, supersession, blocking failure, and any ambiguous event must cause an addressed or generic drain wake. Preserve original event hash and binding; never place untrusted free text in the wake summary. A pure Fable guard may audit this classification but must not itself mutate claims, emit as Tools, or grant authority.
2. Integrate the classifier into the hash-pinned native relay and Lead entrypoint as one immutable, versioned package. The relay must observe durable bridge transitions, including a verified claim release and a task dependency completion, rather than waiting for an unrelated next inbound event or treating `codex queue` acceptance as turn readiness. Wake the exact current session/thread only after identity and claim-scope checks. Unknown identity fails closed and is surfaced for reconciliation.
3. Persist a per-lane event cursor, processed watermark, and one outstanding delivery identity. On crash or restart, replay unprocessed events and reconcile the queue receipt before any resend. Mark an event processed only after the lane has consumed and dispositioned it; make duplicate deliveries idempotent. A late reply or safety control may bypass benign-notice coalescing. No paid idle model polling is needed; use the installed low-cost event observer and bounded health checks.
4. Preserve scoped HOLD and cancellation precedence at every gate. An operational wait may clear automatically only on the verified condition that caused it; a safety HOLD remains stopped until its named release condition is met. A stale-lease release clears only the claim's lease, not its task policy. No agent may write outside its live, disjoint claim or use a peer's identity.
5. Test a whole-package exact head: real PowerShell 5.1 and 7 envelopes, owner/dispatcher routing, unknown and ambiguous dispatcher, stale session/UUID, duplicate events, tail gaps, restart replay, completed-turn receipt, open-request re-evaluation, HOLD/cancel precedence, and code-root/package hash parity. Require independent RCO review and CI on that exact head before any controlled, operator-authorized rollout. Canary one lane, measure an observation interval, and roll back the immutable package on missed delivery or a safety violation.

The proposed longer-term design must remain compatible with the Bridge V2 plan's F1 wake telemetry, F7 single outstanding durable wake, and F30 targeted validated wake content; this native Lead/Tools slice implements none of those complete plan features. F1 would measure no-op ratio, delay and missed actionable events; F7 would supply the durable replay/receipt lifecycle; F30 would supply binding-aware classification and exact fetch. The local F1/F7/F30 plan is in `C:\Python\WD_BRIDGE_V2_PLAN_CURRENT.md` and is only a plan. Measure actual end-to-end continuity from durable event to lane disposition with explicit start/end timestamps; do not infer continuous operation from one callback.

## Native Lead/Tools operational limits and manual reconciliation

This section describes the current integration candidate in `ops/windows/reboot/start-wd-tools-consumer.ps1`, not a deployed guarantee and not the full Bridge V2 feature set. It covers the native Lead/Tools continuity guard only; Claude Monitor is unchanged. The pure guard receives a **checkpoint-only** snapshot. Its empty request/event arrays are explicitly not a complete canonical-log claim. An eligible overdue checkpoint causes one bounded *reconciliation* message to the launcher's verified thread, not automatic acceptance of a dependency or execution of a task. The native host checks the durable condition every 60 seconds without paid idle model polling. [Official OpenAI documentation](https://developers.openai.com/blog/mastering-codex-remote-for-engineering) describes Queue as sending a prompt after the current response; local `codex queue` acceptance likewise proves only that the exact-thread message was queued, not that a turn ran, a side effect completed, or a task finished.

The worktree-local ledger is `.codex-audit/wd-turn-loop/continuity-v1-<verified-thread-id>.json`, with schema, agent and thread checked before use. A key binds agent, guard action and the checkpoint's task/status/next-action/wakeup progress hash; a formatting-only checkpoint rewrite does not reset the budget. The launcher writes `submitting` **before** calling Queue, then records `queued` with its queue ID after exact-thread acknowledgement. A `submitting`, unreadable, oversized, wrong-identity or otherwise uncertain entry blocks automatic resend. Any queued entry younger than one hour rate-limits another recovery; after an hour, an unchanged key is a stall requiring operator reconciliation and an alert, not another wake for the same work. The ledger has a 128 KiB file bound and a hard 256-entry cap. Reaching the cap blocks further automatic recovery; no automatic pruning or blind ledger deletion is safe. Ordinary addressed bridge delivery remains a separate path.

For a blocked or stalled native continuity entry, an authorized operator or reviewer should:

1. Preserve the current bytes and hashes of the per-thread ledger, `continuity-v1-alert.json`, compact checkpoint, native bridge-wake state, and any notice/queue receipts. Verify the installed generation, agent, launch worktree and **exact** launcher-recorded thread ID; never infer a thread from a recent filename or another lane.
2. Use the hash-pinned **read-only** canonical bridge snapshot reader to inspect the exact task's assignments, claims, bound replies, processing receipts and all relevant HOLD/cancel/veto/correction events. A compact view is only an overview. Avoid a reader mode that drains or sweeps while collecting forensic evidence. Compare the checkpoint and its blocker/wakeup fields against that canonical history; a release of a stale claim does not release a safety HOLD.
3. Correlate each ledger entry's key, task, checkpoint SHA, status, timestamp and queue ID with **read-only evidence from the same native Codex thread**. Distinguish `submitting` (delivery uncertain), `queued` (accepted for later delivery), an observed turn, and an independently verified task disposition. Absence of a visible turn or an inaccessible queue history remains **unknown**; do not resend on that basis. Preserve conflicting or incomplete receipts and histories for review.
4. If the exact evidence establishes a completed effect, record that finding without replaying it. If a task remains eligible, re-check its present claim and write scope plus every explicit HOLD and cancellation before a separately authorized continuation. If the one-hour stall or 256 cap remains unresolved, retain the alert and request an evidence-based maintenance decision; any archival or compaction policy needs a separate reviewed procedure that preserves ambiguous entries and proves which keys can no longer suppress a duplicate. Never erase the ledger just to free capacity, override a HOLD, or label a task complete from queue acceptance.

The operational report must state the observation interval, exact head/generation, queue and bridge evidence available, unresolved unknowns, and who owns the next decision. A durable `alert` or `unknown` is a request for reconciliation, not proof that the lane has failed or that an automatic retry is safe.

## Rollout boundary

The current native relay is in the installed c5f7 package, while the persistent source repository may be at another head. Integrate on a verified c5f7 descendant, require clean source and exact package manifest, then use the existing dry-run/stage/apply and controlled handoff gates. The installer requires the Git common directory to be `C:\Python\project2\.git`, a clean reboot/bootstrap source set, a branch with upstream, and upstream HEAD equal to the source HEAD **before StageOnly**. StageOnly then verifies and leaves a commit-addressed bundle staged while leaving machine wrappers, pointers, tasks and live sessions untouched; activation is a separate cold switch. In the read-only inspection of the Lead integration worktree at `757c38c6` on 2026-09-29, the common Git directory and upstream HEAD matched, but `ops/windows/reboot/start-wd-agent.ps1` and `ops/windows/reboot/start-wd-tools-consumer.ps1` were modified. Those dirty reboot sources are a current StageOnly preflight blocker; recheck after Lead's own commit/push rather than assuming they remain dirty or are otherwise deployable. This ADR and the local candidate commit do not authorize live deployment.
